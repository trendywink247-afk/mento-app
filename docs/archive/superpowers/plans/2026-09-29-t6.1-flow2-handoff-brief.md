The Maestro native-e2e safety net for the Expo 52→57 upgrade (T6.2). Three flows

## What's proven — for real, on a real emulator, for the first time ever

**Flow 1 (`onboarding-first-message.yaml`) passes completely, end to end.** Real cold
launch, real onboarding (role fork, age gate, companion pick), real chat screen, a real
message sent and delivered. This had never happened before this session — the whole
CI job had never even booted the app correctly until fixes below landed.

**Flow 2 (`two-party-chat.yaml`) gets all the way to sending its own message too**, then
stalls waiting for the mentor's reply to render. That's the one open problem — see below.

**Six real, evidence-backed infrastructure bugs found and fixed** (commits on
`feat/ws6-t6.1-maestro-flows`, newest first as of this brief — `git log` for exact SHAs):

1. `fix(e2e): 150s for the mentor-reply wait` / `give the mentor-reply wait real headroom` —
   timeout tuning for flow 2 (superseded by the open problem below — don't trust these
   numbers as "the fix," they were good-faith increments before the real cause was found).
2. `ci(maestro): capture mentor-bot.log/.exitcode in failure diagnostics` — the diagnostic
   capture this brief's evidence came from.
3. `fix(e2e): give mentor-bot enough runway to see flow 2's message` — raised mentor-bot's
   own `--timeout` from 60 to 150 (real fix, not superseded — mentor-bot génuinely needs
   this long to find the match).
4. `ci(maestro): disable Sentry's release source-map upload` — `SENTRY_DISABLE_AUTO_UPLOAD:
   "true"`. Sentry's Android Gradle plugin only runs its upload task for release variants;
   this repo never configured CI Sentry auth (deliberately — it's a throwaway test build).
5. `fix(ci): build assembleRelease, not assembleDebug` — **the load-bearing fix.**
   `expo-dev-client`'s entire launcher implementation lives in an Android **debug** source
   set (`expo-dev-launcher/android/src/debug/java/...`) — it is not compiled into a release
   build's classpath at all. No debug-build Gradle property can skip it (a `debuggableVariants
   = []` attempt, still visible in an earlier commit, was tried and proven not to work — real
   screenshot evidence: the emulator sat on dev-client's own "Development servers / npx expo
   start" screen). Only building release omits the code. No new signing infra was needed:
   `expo prebuild`'s generated `android/app/build.gradle` already has
   `release { signingConfig signingConfigs.debug }` — release builds sign with the same
   auto-generated debug keystore debug builds already use.
6. `fix(ci): rewrite the emulator script for its real per-line execution model` — verified
   directly from `reactivecircus/android-emulator-runner`'s own TypeScript source
   (`script-parser.ts` + `main.ts`): the whole `script:` YAML block is split on newlines and
   each line runs as an **independent `sh -c` process** — no shared shell state (variables,
   traps, background jobs, `wait`) survives across lines. This silently broke both a
   diagnostic trap (rewritten as inline `||` handlers per `maestro test` line) and
   mentor-bot's original backgrounding (`( node ... & echo $! > pid )` then `wait` on a
   later line — rewritten as `nohup` + a polled exit-code file).
7. `ci(maestro): enable KVM group perms before launching the emulator` — this action's own
   documented required step for GitHub-hosted Linux runners, simply missing from the
   original workflow.
8. `ci(maestro): reclaim ~20GB of unused preinstalled toolchains` /
   `build the debug APK for x86_64 only` — two separate disk-exhaustion fixes (the Gradle
   build itself, then the emulator-runner's own SDK/system-image download).

All verified against real evidence (actual CI run logs, actual downloaded screenshots via
the `maestro-failure-diagnostics` artifact this session wired up — see "How to get evidence"
below), not guessed. `actionlint` clean throughout; every multi-line shell fix was
independently syntax-checked under real `dash` (this action's actual interpreter) before
pushing.

## The open problem: flow 2's mentor reply never renders

**Not a timing issue — proven by direct visual evidence, not just repeated timeouts.**

Sequence, most recent run (`36492936240`, session 48):
- `mentor-bot.mjs` starts (via `nohup`), connects, authenticates, finds the match, watches
  the Stream channel, detects the member's message, sends its reply, exits 0. Its own log
  (`mentor-bot.log`, captured as a workflow artifact — see below) shows a completely clean
  run: `mentor-bot: member message seen, replying` / `MENTOR_BOT_OK`.
- The member's app shows the sent message with a **"Read"** receipt — meaning mentor-bot's
  side genuinely opened/watched the same conversation the member is in.
- The flow's own `extendedWaitUntil` (waiting for the reply text `"I'm here — tell me more
  when you're ready."` to become visible) times out anyway — three consecutive attempts at
  increasing timeouts (45s → 90s → 150s) all failed, each landing just past its own limit
  (91.7s against a 90s budget; 152s against a 150s budget).
- **The screenshot at the final 150s timeout shows the chat screen with plenty of empty,
  unobstructed space below the member's own message — no scroll/viewport issue, no
  keyboard obstruction. The reply bubble is simply not there.** (Artifact:
  `maestro-failure-diagnostics` on run `36492936240`,
  `step-017-assertCondition-I'm_here_—_tell_me_more.png`.)

The pattern — mentor-bot's own Stream API call to send the message succeeds, but the
member's real-time client never renders it, no matter how long the flow waits — points at
something in the **delivery path**, not a slow round trip. Timeout increases were the wrong
lever three times in a row; don't reach for a fourth one without new evidence.

### Hypotheses to check, roughly in priority order

1. **Channel/conversation identity mismatch.** `mentor-bot.mjs` logs the exact
   `stream_channel_id` it connects to (`active conversation <id>, channel <id>`). Confirm
   the member app's own `ChatScreen`/`ChatScreen.web.tsx` (`apps/mobile/components/chat/`)
   is actually watching that same channel id — not a stale one cached from a previous
   screen, not one resolved differently by a race in the match→channel-assignment flow.
2. **A real-time subscription gap specific to this exact build.** This is the **first-ever**
   test of the app's real-time chat behavior on a genuinely fresh, freshly-installed,
   cold-launched **release** build in an automated (non-interactive) context — every prior
   real-world use of this chat screen has been on a debug build via Expo Go/dev-client or
   manually driven. Check whether `stream-chat-expo`'s `Channel`/`Chat` provider actually
   calls `.watch()` / subscribes to `message.new` promptly after the screen mounts in a
   release build specifically — Hermes bytecode + release JS minification/bundling
   differences (though ProGuard/resource-shrink are confirmed OFF, see commit 5 above) could
   still matter for timing-sensitive subscription setup.
3. **WS5's own-chat merge landing on master mid-session.** PR #9 (WS5, own-chat server
   groundwork — `docs/superpowers/plans/2026-09-20-mento-program-plan.md` §WS5) merged to
   master *during this same session*, before the T6.1 branch's `git merge origin/master`.
   WS5's own module docstring states "nothing user-facing changed: chat still runs on
   Stream" — meaning this should be a non-issue — but that claim has not been independently
   re-verified against the exact code path this Maestro flow exercises. Worth a quick,
   explicit check: confirm the member `ChatScreen` genuinely still uses
   `lib/streamClient.ts` (Stream) and not any new own-chat WebSocket path, on this exact
   branch.
4. **A genuine app-side bug that's always been there, just never observed.** Given this is
   the first time this exact interaction (member sends, a *different, independent* client
   replies via raw Stream API — not through the app's own mentor console UI) has been
   exercised end-to-end on a real device, it's possible the member app's real-time listener
   has a real gap that manual testing (which usually has a human on both ends, both apps
   open and focused) never surfaced.

### How to get evidence without guessing

The workflow (`.github/workflows/maestro.yml`, "Run the three flows on a real emulator"
step) captures `logcat.txt` + `maestro-debug/` (screenshots, `maestro.log`,
`mentor-bot.log`, `mentor-bot.exitcode`) as the `maestro-failure-diagnostics` artifact on
any flow failure — download via `gh run download <run-id> -n maestro-failure-diagnostics`.
`logcat.txt` in particular has never been closely read for this specific failure — it was
pulled every time but attention went to the screenshot and `mentor-bot.log` first. It may
contain the app's own `ReactNativeJS` console output, which could show a Stream SDK error,
a failed `.watch()` call, or silence where an event should have logged.
